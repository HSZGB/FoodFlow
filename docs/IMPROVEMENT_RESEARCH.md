# FoodFlow 二次改进调研与取舍

> 说明：本文是历史改进记录，保留 Ours-Balanced/Ours-Full 等消融讨论；当前默认运行、demo、报告和 PPT 主线已收敛为 Popular、BPR-MF、UserOnly、Seq-Tuned、Seq-xQuAD-Tripartite。

本轮改进围绕课程评分标准展开：算法设计思路、算法任务、实验结果、结果分析、代码说明、创新性和展示效果。目标不是把课程项目强行升级成工业级外卖系统，而是在可运行、可解释、可复现的前提下补足最容易被追问的短板。

## 1. 创新性如何加强

原方案的核心创新是“用户-商家-骑手”的三方闭环：推荐列表产生订单，订单进入骑手匹配，履约结果再用系统级指标评价推荐策略。这个方向比单纯 Top-K 推荐更贴近外卖业务，但如果只有一个固定权重的 `Ours-Full`，容易被质疑为手调公式。

本轮新增 `Ours-Balanced`，把三方重排改成可参数化版本：

- `UserOnly`：用户准确性优先。
- `Ours-Balanced`：提高用户偏好权重，同时保留 ETA 与供给约束。
- `Ours-Full`：更强调商家公平与履约可行性。

这样可以把结论从“我设计了一个模型”升级为“我展示了多目标推荐中的权衡路径”。

## 2. 指标不是全部最优时如何讲故事

外卖推荐不应只追求 Recall@K。更合理的故事是：

1. `UserOnly` 证明用户画像特征有效，通常离线 Recall/NDCG 更高。
2. `Ours-Balanced` 作为折中策略，观察用户准确性与履约约束是否可以兼顾。
3. `Ours-Full` 牺牲部分离线准确率，但在动态履约仿真中争取更低 ETA、更低超时率和更高平台效用。

因此，答辩中不把“Recall 第一”作为唯一胜利条件，而是强调多方平台的 trade-off：用户满意、商家曝光、骑手负载和平台履约共同构成评价目标。

## 3. 可视化如何改进

原项目已有单指标柱状图，但展示效果偏“结果表的图片版”。本轮新增：

- `tradeoff_recall_coverage.png`：准确性与商家覆盖率权衡。
- `tradeoff_eta_utility.png`：平均 ETA 与平台效用权衡。
- `tripartite_scorecard.png`：用户、商家、平台三方 scorecard。
- Streamlit 三页看板：三方推荐案例、实验指标对比、图表看板。

这些图更适合支撑“讲好故事”的课程要求。

## 4. 为什么不直接补 LightGCN/KGAT

另一份调研方案提到 LightGCN、KGAT/KGCN 和知识图谱。它们能提高算法深度，但当前项目存在两个现实约束：

- TRD 的公开文本数据可以稳定支持用户-商家推荐，但没有完整骑手轨迹和真实派单记录。
- 课程项目更看重系统设计、开发与优化闭环；强行加入图神经网络会显著增加依赖、训练时间和复现风险。

因此本轮选择低风险增强：保留可解释三方重排，增加权重敏感性、数据审计和系统级可视化。LightGCN/KGAT 仍保留为后续增强方向，而不是核心验收路径。

## 5. 完整 TRD 与抽样边界

项目已经下载真实 TRD txt 文件，但运行结果可能有两种模式：

- `make preprocess`：默认抽样 5 万训练订单，适合 CPU 快速复现实验。
- `make preprocess-full`：使用完整 `orders_train.txt`，适合最终严谨验收。

本轮新增 `make audit`，自动输出：

- 原始训练订单数
- 处理后训练订单数
- 训练订单使用比例
- 当前训练模式是 `sampled` 还是 `full`
- 骑手数据是否为合成 proxy

这样“有没有完整跑 TRD”可以由文件证据说明，而不是口头解释。
