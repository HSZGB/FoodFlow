# FoodFlow Demo 小版本自评

## 本轮解决的问题

1. 修复 `make demo` 中 Streamlit 1.39.0 的图片 API 兼容问题。
   - 旧版 `st.image` 不支持 `use_container_width`，本轮增加兼容函数，自动切换到 `use_column_width`。
2. 将 demo 从“表格展示”升级为“推荐工作台”。
   - 默认展示用户 `8`。
   - 支持输入任意用户 ID，避免 20 万用户下拉框影响现场演示。
   - 用商家推荐卡片展示排名、评分、均价、距离、ETA、用户偏好、商家公平、履约速度、供给稳定。
3. 强化三方推荐的直观表达。
   - 用户侧：用户画像、历史品类偏好、Top-K 推荐卡片。
   - 商家侧：公平分、曝光补偿、覆盖率与长尾曝光指标。
   - 骑手侧：同一订单在最近骑手、最小 ETA、负载感知策略下的 ETA 对比。
4. 增加空间和链路可视化。
   - 使用散点图展示用户、推荐商家、下单商家和匹配骑手的位置关系。
   - 使用 Sankey 链路图展示“用户 -> 商家 -> 骑手 -> 履约结果”。
5. `make demo` 默认切换为 conda 环境，减少展示环境与实验环境不一致的问题。
6. 增加策略切换与同一用户策略对比。
   - 可在 `UserOnly`、`Ours-Balanced`、`Ours-Full` 之间切换。
   - 同屏展示三个策略的 Top3 商家、平均用户偏好、平均商家公平、平均 ETA、平均供给和推荐重合数。
7. 增加固定案例用户和推荐理由筛选。
   - 默认案例保留用户 `8`。
   - 自动提供复购活跃型、高消费型、价格敏感型等案例，便于现场讲故事。
   - 推荐卡片中将复购、品类偏好、价格匹配、履约较快、曝光补偿做成可筛选标签。

## 对照评分项的提升

| 评分项 | 本轮贡献 |
|---|---|
| 算法设计思路 | 分数组成、三方链路和骑手策略对比让 Ours-Full 的设计不再只停留在公式或表格中。 |
| 算法任务 | demo 直接串起推荐、模拟下单、骑手匹配，任务链路更完整。 |
| 实验结果 | 指标故事线展示 Recall/NDCG、Coverage、ETA、Timeout、Utility 等核心指标。 |
| 结果分析 | 用“准确率不是唯一目标，履约指标验证三方策略价值”的方式组织结果。 |
| 代码及说明 | 增加 demo 辅助函数和测试，减少 Streamlit 版本兼容风险。 |
| 创新性 | 三方闭环的可视化更清楚，能直观看到用户推荐、商家曝光和订单派给骑手。 |

## 仍可继续加强的建议

1. 增加“仿真播放”视图，用时间步展示午餐高峰中订单如何逐步分配给骑手。
2. 如果答辩现场时间允许，可以继续人工挑选 2 到 3 个更有戏剧张力的用户案例，分别代表复购型、价格敏感型、履约敏感型用户。
